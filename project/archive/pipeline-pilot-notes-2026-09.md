# Multi-model pipeline pilot notes (2026-09-29 to 09-30)

Moved from `project/BACKLOG.md` on 2026-10-07. Lessons from the pilots when Codex implemented and Gemini reviewed; that setup is legacy (`project/orchestration/README.md` "History"). The lessons still in force live in `project/orchestration/reviewer-primer.md`.

## Notes (from the Phase 2 review/fix pilot, 2026-09-29)

First real test of Codex operating with the owner directly (no Claude orchestrating in real time) via the `AGENT_HANDOFF.md`/`CODEX.md`/`AGENTS.md` handoff system, followed by Claude reviewing after the fact.

- **A detailed, accurate handoff doc is worth the overhead.** Every claim in Codex's `AGENT_HANDOFF.md` checkpoints (test counts, live-check results, exact commands, what was and wasn't verified) was independently re-checked by Claude and found accurate — including honest admissions like "this is not cited Bedrock acceptance" when the fake LLM was still in use, and clearly flagging Gemini's review as attempted-but-failed rather than implying approval. This is what made a full-phase after-the-fact review tractable instead of a blind audit from zero context.
- **Autonomous multi-task runs need a review gate regardless of who's driving.** Codex correctly followed its own per-task commit discipline (7 clean, single-purpose commits), but nothing enforced landing on a branch instead of `main` or stopping for review before merge — because the rule was only ever stated for Claude-led work. The result: ~2,400 lines of security/cost-relevant code (rate limits, spend caps, cache correctness) sat on `main`, unreviewed by anyone, until asked for directly. The review found the hard parts (Redis Lua-script atomicity, answer-cache model scoping) were done correctly — but also one Critical latent bug a pre-merge review would have caught. Fixed going forward via the worktree policy in `project/CODEX.md` (now `project/archive/CODEX.md`).
- **A reviewer catching a fix that's too narrow is itself a normal, healthy part of the loop, not a failure.** The first grounding fix (Fix 4) correctly solved the one reported hallucination but was hardcoded to a single source file; a second review pass caught that the same corpus has plenty of other equally-exposed "planned" content, and Codex generalized it in one more small round-trip. Two-stage review (implement → review → fix → re-review) caught this exactly the way it's supposed to.
- **A live before/after reproduction is a much stronger verification artifact than a description of a fix.** For the grounding fix specifically, Codex re-ran the exact original hallucination-producing question against both the old and new code and reported the literal before/after answer text, twice (once per fix round). This is categorically more convincing than "added grounding instructions" — it's proof the specific reported failure is gone, not just that code changed in the right area.
- **Running the actual eval script against real data closed a gap that reading code alone couldn't.** The Phase 2 plan required a real Titan retrieval baseline as its acceptance signal, but this had been skipped in favor of only a fake-model smoke baseline. It turned out to be a single command against already-embedded data (recall@5 0.8667 vs. the fake baseline's 0.4667) — cheap to close once noticed, easy to silently leave undone otherwise. Worth checking a plan's stated "done when" criteria literally, not just whether the code paths exist.

## Notes (from the Phase 3b pilot, 2026-09-29)

Wiring the frontend to the real backend SSE endpoint — same corrected roles as Phase 3a (Codex implements against an exact spec, a Sonnet subagent verifies live against a real running backend and fixes what it finds, Claude subagent reviews since Gemini's quota is still exhausted).

- **A well-specified abstraction pays off exactly as intended.** The backend's `EmbeddingProvider`/`LLMProvider` interfaces were built in Phase 1 specifically so Bedrock could later slot in without touching the API/worker/queue — this phase proved the same design principle from the other side: because the SSE contract (DD1 §8) was already fully implemented and stable, wiring the frontend to it required *zero* backend changes, and Codex could implement the entire frontend side from the contract alone, correctly, on the first pass (no Critical findings from either the live-verification or code-review passes).
- **A synchronous double-submit test is a meaningfully stronger concurrency check than a fast double-click.** The Sonnet verification agent fired two `form.requestSubmit()` calls back-to-back in the same tick specifically to race React's own batched state updates — this is the exact scenario a ref-based guard (`requestInFlightRef`) is needed for and a plain `isStreaming`-state guard would sometimes miss (both synchronous calls can read the same stale `isStreaming` value before either write lands). Worth using this pattern (not just a slow manual double-click) whenever verifying a submit-guard on any future form/action in this app.
- **A "no bugs found" live-verification pass doesn't mean skip code review.** The live-verification agent found zero bugs end to end (both corpora, mobile sheet, the double-submit race); the subsequent code-quality review still caught two real Important issues invisible to behavioral testing — a `DoneEvent.mode: "retrieval_only"` response would silently render an empty, response-less chat bubble (unreachable with today's fake backend, which hardcodes `mode: "full"`, but a real contract value Phase 2's rate-limiting will actually trigger), and `aria-live="polite"` on the whole chat list would flood/repeat screen-reader announcements on every streamed token. Neither shows up by clicking through the happy path — both are the kind of finding that specifically needs a reviewer reading the code, not just exercising it. **Lesson: live verification and code review catch different bug classes; neither substitutes for the other, even when one comes back completely clean.**
- **Fixing a currently-unreachable defensive gap is often still worth it when it's cheap.** The `retrieval_only` fix cost one `if` branch and a line of copy, even though nothing in today's backend can trigger it — worth doing now rather than waiting for Phase 2 to reintroduce the same review finding, since the fix location (a `DoneEvent.mode` check already being threaded through `onDone`) was already open and in context.

## Notes (from the Phase 3a pilot, 2026-09-29 → 09-30)

First real frontend run of the corrected roles (`project/orchestration/README.md`): Codex writes initial component code where its network-free sandbox allows, a Sonnet subagent (not Opus) does the npm/dev-server/browser-verification/debugging loop, Claude subagent reviews (Gemini's quota was already exhausted for this whole phase).

- **A Sonnet subagent dispatched via the `Agent` tool with `model: "sonnet"` genuinely routes to Sonnet** (self-identifies as `claude-sonnet-5`) and has full tool access (no network sandbox, unlike Codex) — confirmed by direct test before relying on it. This makes it the right fit for exactly the work Codex's sandbox can't do: installing packages, running a dev server, and real `claude-in-chrome` browser verification.
- **CSS-only hiding (`hidden md:contents`) still mounts the component.** Codex's mobile-layout diff hid the desktop `ArchitecturePanel` (a React Flow instance) below `md` with CSS alone, which left it permanently mounted-but-invisible at 0×0 on mobile, plus a second live instance whenever the mobile bottom sheet was also open. Not caught by `tsc`/lint/build (all passed) — only surfaced by dispatching a Sonnet subagent to actually load the page at multiple viewport widths and check `document.querySelectorAll('.react-flow').length`. Fixed by conditionally *mounting* based on a `useMediaQuery` hook instead of CSS-hiding, making the two `ArchitecturePanel` instances mutually exclusive by construction (derived boolean, not a `useEffect` sync). **Lesson: for any component with real side effects on mount (observers, listeners, third-party libs), CSS `hidden`/`display:none` is not equivalent to not-mounted — verify what's actually in the DOM, not just what's visually hidden.**
- **A clean review can still surface one real, worth-fixing issue even with no Critical/blocking findings.** The Claude-subagent code review found the mobile bottom sheet declared `aria-modal="true"` without any Escape handler or focus management — a real accessibility gap, correctly scoped by the reviewer as "Important, but reasonable to defer for a skeleton phase." Fixed anyway (cheap, ~2-line core change) rather than deferred, since it was low-effort and closed a real gap; the reviewer's other two suggestions (scroll lock, resize-edge-case reset) were accepted as documented/deferred since they're lower value at this stage. **Lesson: "not Critical" and "not worth fixing now" aren't the same judgment — weigh fix cost, not just severity, when deciding whether to defer a review finding.**
- **`pre-commit` needs the project venv activated** (`source .venv/bin/activate`) — it's installed there, not on the system PATH; committing without activating fails with `pre-commit not found` rather than silently skipping hooks. Worth remembering every session, not just once.

## Notes (from the Phase 1b pilot, 2026-09-30)

- **Real integration tests that enqueue onto a shared, long-lived Redis Stream can pollute each other across test files if a test doesn't fully consume what it produced.** A test in `test_ask_endpoint.py` called the real `enqueue_retrieval_job` (correctly, to test real enqueue behavior) but simulated the worker's output directly instead of running a real worker to drain the job — leaving an orphaned, never-acked message sitting in `retrieval:jobs`. Redis Streams consumer groups deliver never-yet-delivered messages in stream order regardless of which consumer asks, so a *later* test file's brand-new consumer picked up that stale orphaned message instead of the one it had just added itself, and failed for a confusing reason (assertions about "the message I just enqueued" didn't match, because the code was actually processing someone else's leftover job). Symptom looked exactly like a real regression in freshly-changed code (a shared-helper refactor had just landed) and cost real time to root-cause via manual reproduction before the actual cause (test isolation, not implementation) became clear. **Lesson:** any integration test that enqueues real work onto a shared queue/stream must fully drain what it added (consume+ack, or delete the specific message) in a `finally` block — don't assume "my test passed" means "my test left no trace." Worth periodically checking `XLEN`/consumer-group lag on long-lived dev Redis instances if tests unexpectedly start failing for no code-visible reason.
- **The literal, manual "run the real thing end to end" step remains the actual bar, not passing tests.** All 72 automated tests passed before the real `curl -N` verification — but that verification is what actually proves DD1 Phase 1's done-when criterion (`docs/DESIGN.md` §17) is met: started the real worker and API processes, hit the real endpoint twice (once per corpus), and watched real `stage`/`retrieval`/`token`/`done` events stream correctly, `seq` staying strictly increasing across two separate OS processes sharing state only through Redis. No test suite, however thorough, is a substitute for this specific check when the deliverable's actual acceptance criterion is "watch it work."

## Notes (from the Phase 0 pilot, 2026-09-29)

Set up: Claude = architect/orchestrator (writes blueprints, does final judgment calls); Codex CLI = implementer; Gemini via `agy` (Antigravity) CLI = spec/quality reviewer. Findings worth remembering next time this is used:

- **Model access is plan-gated, not just a `-m` flag.** Under a ChatGPT (non-Pro) login, Codex only accepts `gpt-6-luna` — `sol`/`astra`/`terra`/bare `gpt-6` all reject with "not supported when using Codex with a ChatGPT account." After upgrading to ChatGPT Pro, `gpt-6-sol` worked and produced visibly cleaner, more focused output than `luna` (no wasted exploratory turns). Always verify which models are actually usable before relying on a model choice in a plan.
- **Codex's `workspace-write` sandbox cannot write git-worktree metadata.** A worktree's `.git` lives in the main repo's `.git/worktrees/<name>/`, outside the sandboxed workdir — so Codex can create/edit files but can't `git commit` inside a worktree. Working pattern: Codex implements, the orchestrator verifies and commits.
- **Codex needs `--dangerously-skip-permissions`-equivalent flags for read-only too, and `agy` needs `--mode plan --dangerously-skip-permissions` for headless review** — neither CLI's non-interactive mode has a native structured status protocol (DONE/BLOCKED/etc.) the way Claude subagents do; that has to be spelled out in every prompt.
- **Static review (even a good one) doesn't catch integration bugs.** Codex + two separate Gemini reviews all missed that MySQL 8's default auth (`caching_sha2_password`) needs the `cryptography` package for `aiomysql` — only found by actually running `docker compose up` and hitting `/readyz` for real. The lesson: the pipeline still needs an orchestrator-run, real end-to-end verification step; review agents (of any vendor) reading code is not a substitute for running it.
- **Gemini's reviews (via `agy`) were genuinely thorough** — caught nothing wrong, but gave real file:line-cited reasoning and independently re-ran tests/lint rather than trusting the brief.

## Notes (from the Phase 1a pilot, 2026-09-29)

Same roles as Phase 0 (Claude orchestrates, Codex implements, Gemini reviews), applied to a much bigger, more integration-heavy phase (schema, providers, 4 chunkers, an ingestion job tying them together). More findings:

- **Codex's sandbox has zero network access, not even loopback.** It's not just "can't reach the package index" (Phase 0's finding) — it cannot reach `127.0.0.1:3306`/`127.0.0.1:6379` either, even with `docker compose` running on the host and the ports published. Any test requiring a real DB/service connection has to be skipped inside Codex's own dispatch and re-run independently by the orchestrator afterward. Codex handles this well when told about it upfront (self-reports `DONE_WITH_CONCERNS` and says exactly what it couldn't verify, rather than guessing) — always tell it explicitly in the dispatch that this limitation exists so it plans its own testing around it (unit-testable pieces now, integration deferred).
- **Behavioral specs work well for Codex on genuinely algorithmic tasks**, not just boilerplate. The Markdown chunker (merge-forward/overlap-window logic) and the ingestion script's denylist/secret-heuristic design were both given as prose specs, not literal code, and Codex made sound, well-reasoned implementation choices — a shift from Phase 0's "give exact code" style that saved real authoring time without costing quality, *as long as the review stage stays rigorous* (see below).
- **First-pass review still found two real Critical bugs on the chunkers task** (Terraform block detection truncating on inline nested braces; Python decorators getting detached from their functions) — both passed Codex's own tests, because Codex's synthetic fixtures didn't happen to exercise those cases. Gemini's review caught both, and a second review round after the fix caught that the fix itself had a residual gap (comment/string-literal contents can still throw off brace counting). **Two-stage review isn't paranoia — real, non-obvious bugs get through self-testing regularly, even from a strong implementer model.**
- **Not every review finding needs another round-trip.** After the second Terraform/decorator fix, the remaining findings (brace-counting inside string literals/comments, multi-line decorators, typed TS arrow functions) were accepted as documented known limitations instead of triggering a third fix cycle, because: no real Terraform or TypeScript files exist in this repo yet to be affected by them (those land in later milestones), and fully solving the string/comment-stripping issue needs real tokenization — disproportionate effort for code with zero real input right now. Judgment call: fix what's Critical or affects real content now; document (in the code, in a docstring, not just in chat) what's deferred and why, rather than chasing every edge case a reviewer can hypothesize.
- **Reusing already-verified throwaway code is a legitimate, fast path.** The Markdown chunker built during the earlier model-comparison pilot (see above) was copied directly into this repo rather than re-dispatched from scratch — saved a full Codex round-trip. Worth remembering: keep useful throwaway outputs from exploratory/comparison work instead of discarding them.
- **`detect-secrets`'s pre-commit hook will flag legitimate test fixtures repeatedly** (hardcoded dev passwords, fake API keys used to test a secret scanner). This isn't a one-time Phase-0 fluke — it happened again in Phase 1a (a test-fixture MySQL password). Expect `detect-secrets scan > .secrets.baseline` to be a routine step after any commit that adds new string literals resembling credentials, not an exceptional one.
- **`agy` reviews on larger/more file-heavy diffs can take longer than the default assumption** — a review covering 4 files (chunkers) or an integration-heavy task (ingestion script) sometimes needs 5-8 minutes, not the ~2-3 minutes smaller Phase 0 reviews took. Give `agy` calls a generous timeout (300-480s) rather than the tool default, especially for anything reviewing more than 1-2 files.
- **Real end-to-end verification keeps earning its keep.** Running the actual ingestion job against real corpus content (not just tests) surfaced a genuinely interesting correctness signal for free: the secret scanner correctly quarantined the ingestion pipeline's own test file, because that file legitimately contains a fake-AWS-key string as its own test fixture. Nothing broke — but this is exactly the kind of thing that only shows up by running the real thing against real data, not by reading code or running synthetic-fixture tests.

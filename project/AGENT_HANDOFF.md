## Task 5 closed for real: root cause of the Job-recreation bug found and fixed, verified with a real hands-off release — Claude, 2026-09-30

**Active coordinator: Claude.** This closes out the "one still pending confirmation" item from the checkpoint immediately below. Two things happened after that checkpoint, in order:

**1. The pending (a)-(d) verification (does `build-N` actually reach ECR → ImagePolicy → `deploy` → pods) — all confirmed, but pods still needed a manual `kubectl delete job` to pick up `build-12`,** exactly like bug #5 below, which was surprising since PR #17 supposedly already fixed that. A Codex second-opinion review of PRs #20-24 (requested by the owner) independently flagged the same suspicion the owner had: the `kustomize.toolkit.fluxcd.io/force` annotation's value.

**2. Root cause found and fixed (PR #26), not just worked around again.** Per Flux's own docs (`https://fluxcd.io/flux/components/kustomize/kustomizations/`), the per-resource `force` annotation is a **string enum** (`enabled`/`disabled`) — it is *not* the same boolean type as the Kustomization-**spec**-level `.spec.force` field (same word, different knob, different value format). Both `ingest-job.yaml` and `migrate-job.yaml` had `kustomize.toolkit.fluxcd.io/force: "true"`, which Flux silently treats as unset — so the annotation had *never actually worked*, on either the original PR #17 fix or the manual-delete workaround in bug #5 below. It only ever "worked" because a human ran `kubectl delete job` by hand each time and Flux happily recreated fresh objects that then carried the (still-broken) annotation forward, masking the bug.

Fixed the value to `enabled` in both files, merged, and verified with a real release end-to-end: PR #26's merge auto-triggered `build-13`; `ImagePolicy` picked it up, `ImageUpdateAutomation` committed it to `deploy`, and **both Jobs auto-recreated and `api`/`retrieval-worker` rolled out to `build-13` with zero manual intervention** — confirmed directly via SSM (`ingest`/`migrate` both `Complete` on `build-13`, ~114s old; `api`/`retrieval-worker` both on `build-13`). This is the first fully hands-off release this project has ever had.

**Also confirmed correct, from the same Codex review:** `filterTags`/`extract` syntax and `order: asc` (both correct, not bugs). **New findings from that review, not yet acted on** (now in `project/BACKLOG.md`'s Infrastructure & reliability section): (a) a manual `workflow_dispatch` release run against an old ref could still mint a higher `build-N` and get selected — build number alone doesn't prove current-`main` provenance; (b) the release path-filter is missing some Dockerfile-`COPY`'d paths (`corpus/`, `docs/`, `infra/`, `k8s/`), so a merge touching only those could leave the image stale; (c) `sync-deploy-branch.yml` and Flux both push to `deploy` with no retry, so a race could silently drop a sync; (d) `migrate` and `api` share one Kustomization with no explicit ordering — nothing guarantees the migration finishes before the API expecting it rolls out (flagged independently by both the owner and Codex).

**The honest framing: this was not going in circles. Five independent, compounding bugs were found, in order, each real and necessary but not sufficient on its own, because nobody had ever forced a real reconcile before this session.** Read them in order if picking this up fresh:

1. **IMDS hop limit (PR #20, `infra/modules/compute/main.tf`).** First symptom chasing `ImageRepository`'s 401 against ECR. Fixed `http_put_response_hop_limit` to 2. Terraform plan reported **no changes** when applied - it was already correctly set (likely from an earlier local `terraform apply` run while the edit sat uncommitted). Real config, but **not the cause of the 401** - ruled out by curling IMDS directly from inside the `image-reflector-controller` pod and getting a clean 401 *challenge* (proves reachability, not blockage).
2. **Missing IAM permissions (PR #21, `infra/modules/compute/main.tf`).** IAM policy simulation of the `glassbox-instance` role against the repo ARN showed `ecr:DescribeImages`/`ListImages`/`DescribeRepositories` all `implicitDeny` - the registry v2 `tags/list` call needs these; the existing `BatchGetImage`/`BatchCheckLayerAvailability`/`GetDownloadUrlForLayer` (plain docker-pull) permissions don't cover it. Added and applied for real (confirmed via `aws iam get-role-policy` after apply). **Still got 401** after this.
3. **The actual auth bug (PR #22, `k8s/overlays/prod/flux/image-repository.yaml`).** The `ImageRepository` manifest never had `spec.provider: aws` set. Without it, `image-reflector-controller` never attempts the AWS SDK credential chain at all - it sends an anonymous registry request, which private ECR always answers with 401 regardless of IAM permissions. This is the field that actually turns on node-role-based ECR auth. Fixed - **scan started succeeding** (`successful scan: found 8 tags`).
4. **Broken ImageUpdateAutomation commit template (PR #23, `k8s/overlays/prod/flux/image-update-automation.yaml`).** Once scanning worked, `ImageUpdateAutomation` was separately stuck: `template uses removed '.Updated' field. Please use '.Changed' instead.` The bootstrapped Flux version removed the field the original manifest's `messageTemplate` used. Rather than chase the exact replacement field shape (varies across Flux versions), switched to a static commit message. **This unblocked the actual git commit** - `fluxcdbot` successfully committed the tag bump to `deploy` at 2026-09-30T12:39:15Z.
5. **Stale immutable Jobs (manual fix, no PR - owner ran via SSM).** The Kustomization's atomic apply then failed on `Job.batch "ingest"/"migrate": field is immutable` - both Jobs predated the `kustomize.toolkit.fluxcd.io/force: "true"` annotation added in an earlier session (PR #17) and their live objects didn't have it. Owner ran `kubectl delete job -n app migrate ingest` via SSM (Claude is blocked from `kubectl delete` by the auto-mode classifier). Flux recreated both fresh with the annotation baked in, which unblocked the whole apply, including `api`/`retrieval-worker`.
6. **Wrong image reached production (PR #24, `.github/workflows/release.yml` + `k8s/overlays/prod/flux/image-policy.yaml`) - the serious one.** After all of the above, Flux DID roll production to a new image tag: `3842459`. That looked like a real build number but wasn't - it's the short git SHA of an old merge commit (PR #17's `3842459 Merge pull request #17...`), which happens to be all-digits by coincidence. `ImagePolicy`'s `filterTags: {pattern: '^\d+$'}` matched it alongside real build-number tags, and since it's numerically larger than any real build number (`11` at the time), Flux's "highest wins" policy deployed the wrong, arbitrary old commit to production instead of the real latest release. **Fixed** by prefixing build-number tags with `build-` in `release.yml` (`build_number=build-${{ github.run_number }}`) and requiring that prefix in `ImagePolicy`'s filter (`pattern: '^build-(?P<num>\d+)$'`, `extract: '$num'`) - a hex git SHA can never collide with `build-N` again. Merging this PR auto-triggered a fresh release build (`release.yml` is in its own path-filter list), which completed successfully (run visible in Actions).

1. **Critical — no embedding-model isolation in the live retrieval index.** `services/glassbox/ingest/redis_index.py`'s `idx:chunks` schema and `services/glassbox/retrieval/search.py`'s `search_chunks()` have no model tag/filter, only `corpus`.

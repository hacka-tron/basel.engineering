## Latest local checkpoint

**Chat stream resilience (DD2 §6.2, §6.3, §7.4), branch `feature/chat-stream-resilience` (worktree `.worktrees/chat-resilience`; unmerged, not live):** `/api/ask` sends a `: ping` SSE comment after 15 s of quiet and stops generation when the client disconnects. Starlette cancellation is the primary signal and a 1 s `is_disconnected()` poll is the fallback. Stopped requests are logged as `mode='stopped'` with the tokens actually generated (Alembic `0004_query_mode_stopped`). The chat has a Stop button that keeps the partial answer as `stopped` and frees the chat at once, a 45 s client idle watchdog ("Connection lost — try again."), and §6.3 smart auto-scroll with a "Jump to latest" pill. Failed requests appear as friendly assistant replies (20 random generic ones, plus specific rate-limit and budget replies), saved as `error` and never sent as history. The frontend now has `npm test` (Node's built-in runner, no new dependencies), and CI runs it. See DD2 §6.6 and §7.6.

**Conversational chat (DD2 §5), branch `feature/chat-context` (worktree `.worktrees/chat-context`, based on `feature/stress-test-keda`; unmerged, not live):** `POST /api/ask` takes an optional bounded `history` (server keeps the last 6 messages / 4,000 chars). Follow-ups are rewritten into a standalone query (new `rewrite` trace stage) for embedding and retrieval. The answer prompt gets the original question plus untrusted-labelled history, and follow-ups skip the semantic answer cache both ways. The daily budget is enforced in quarter-units (answer 4, rewrite 1): answers stay in the original `budget:llm:{date}` counter, which pre-chat pods also use, and rewrites go in `budget:llm:rw:{date}`. One atomic script checks both against `4 × cap`, so a rolling deploy never loses count of answers. The frontend keeps one conversation per corpus tab in localStorage (`glassbox:conv:v1:<corpus>`, save-on-settle, 7-day expiry, fail-safe), with New chat, per-answer sources, and a Rewrite diagram node. The query log records `turn_index` and `rewritten_query` (Alembic `0003_query_turn_columns`, checked against a throwaway MySQL 8.0 for upgrade, downgrade and re-upgrade, but **not applied to the shared local DB or live**; until it is, the two DB-backed ask tests skip, and `GLASSBOX_TEST_MYSQL_PORT` points them at a migrated DB). Stored chats with an `updatedAt` more than 5 minutes in the future are discarded. See DD2 §5.3.1.

- **DD1 Phase 2 provider boundary implemented in source:** `GLASSBOX_PROVIDER=fake|bedrock` selects embedding and LLM adapters from one factory, validated at FastAPI startup (invalid provider mode, non-positive daily cap, or malformed Bedrock model ID fails app startup, not just the first request). - **Retrieval index is embedding-model isolated:** `idx:chunks` tags each chunk with a hashed embedding-model ID (mirroring the answer cache's existing pattern) and `search_chunks()` filters by the current provider's model — a partial re-ingestion failure during a model switch (a real, previously-observed failure mode) can no longer leave a stale-model vector silently mixed into live KNN search results for a corpus. A corpus with zero chunks matching the current model returns "I don't know from what I have." without an LLM call or budget charge, not a crash.
- **Phase 2 caches:** `EmbeddingCache` (Redis, SHA-256 key including model identity, 7-day TTL), `RetrievalCache`/`ChunkCache` (corpus+version+model scoped, 1-hour/1-day TTL), and `AnswerCache` (Redis Search vector index, 24-hour TTL, cosine similarity >=0.95, scoped by corpus+version+model so a provider switch can never replay a stale model's answer — verified with a test that flips the model mid-test). A Redis `NX`/`PX` lock (15s TTL) now covers the answer-cache miss-to-write path — a second concurrent request for the same new question waits up to 3s for the first to finish before falling back to answering independently, closing a previously-unmitigated stampede (verified with a genuine `asyncio.gather` concurrency test, not a sequential one).
- **Phase 2 usage limits:** `RateLimiter` and `DailyBudget` contracts have atomic Redis Lua-script implementations (single `EVAL` call, no read-then-write race). Each salted client-IP hash gets 10 questions per 10 minutes; forwarded IP is considered only from configured trusted proxy CIDRs. A UTC daily cap defaults to 100 generated answers; answer-cache hits don't reserve a slot. At the cap, `done.mode="retrieval_only"` returns source snippets with no LLM call — the frontend (built two phases earlier, defensively, for a path that couldn't fire yet) handles this correctly now that it's reachable.

## Target architecture (full detail in docs/DESIGN.md)

Browser → Cloudflare (TLS/proxy) → Traefik on a single EC2 `t4g.small` (k3s) → FastAPI `api` (also serves the built frontend) + `retrieval-worker` (KEDA-scaled 1-3 once `feature/stress-test-keda` merges and is applied; fixed-replica until then) ↔ in-cluster Redis (cache/queue/vector index) and MySQL (source of truth) → Amazon Bedrock (embeddings + LLM). GitHub Actions builds/pushes each merge to `main`; Flux's Image Update Automation watches ECR and deploys automatically, no manual step.

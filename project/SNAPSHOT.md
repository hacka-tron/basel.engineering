- **DD1 Phase 2 provider boundary implemented in source:** `GLASSBOX_PROVIDER=fake|bedrock` selects embedding and LLM adapters from one factory, validated at FastAPI startup (invalid provider mode, non-positive daily cap, or malformed Bedrock model ID fails app startup, not just the first request). Fake remains the default. The Bedrock adapter uses Titan V2 for 512-dimensional vectors and Nova Lite ConverseStream for text (Anthropic Haiku streaming is still blocked by the account's first-time-use form). Ingestion re-embeds unchanged documents when the stored embedding model differs, and stores the selected model ID on each chunk. API and ingestion use the provider interfaces rather than direct Bedrock calls.
- **Retrieval index is embedding-model isolated:** `idx:chunks` tags each chunk with a hashed embedding-model ID (mirroring the answer cache's existing pattern) and `search_chunks()` filters by the current provider's model — a partial re-ingestion failure during a model switch (a real, previously-observed failure mode) can no longer leave a stale-model vector silently mixed into live KNN search results for a corpus. A corpus with zero chunks matching the current model returns "I don't know from what I have." without an LLM call or budget charge, not a crash.
- **Phase 2 caches:** `EmbeddingCache` (Redis, SHA-256 key including model identity, 7-day TTL), `RetrievalCache`/`ChunkCache` (corpus+version+model scoped, 1-hour/1-day TTL), and `AnswerCache` (Redis Search vector index, 24-hour TTL, cosine similarity >=0.95, scoped by corpus+version+model so a provider switch can never replay a stale model's answer — verified with a test that flips the model mid-test). A Redis `NX`/`PX` lock (15s TTL) now covers the answer-cache miss-to-write path — a second concurrent request for the same new question waits up to 3s for the first to finish before falling back to answering independently, closing a previously-unmitigated stampede (verified with a genuine `asyncio.gather` concurrency test, not a sequential one).
- **Phase 2 usage limits:** `RateLimiter` and `DailyBudget` contracts have atomic Redis Lua-script implementations (single `EVAL` call, no read-then-write race). Each salted client-IP hash gets 10 questions per 10 minutes; forwarded IP is considered only from configured trusted proxy CIDRs. A UTC daily cap defaults to 100 generated answers; answer-cache hits don't reserve a slot. At the cap, `done.mode="retrieval_only"` returns source snippets with no LLM call — the frontend (built two phases earlier, defensively, for a path that couldn't fire yet) handles this correctly now that it's reachable.
- **Phase 2 grounding fix:** the prompt now explicitly distinguishes current vs. planned/future functionality — a real hallucination (an `about_system` answer describing the not-yet-built Google Drive connector as current) was reproduced, root-caused (the corpus's own design docs describe future work in plain declarative prose with no current/planned framing), and fixed. The fix generalizes beyond the one originally-reported source: a case-insensitive signal match (planned/deferred/not-yet-built language, Phase 4-7 / Milestone 2-4 references, and still-unbuilt deployment terms like KEDA/Terraform/k3s) marks any matching chunk, not just the one file that produced the first reported hallucination. Documented in code as a known forward-maintenance risk: this is keyword-based, not tense-aware, so it'll need revisiting once Phase 4/5 actually ships and those same keywords start describing real, current infrastructure.
- **Phase 2 retrieval evaluation harness:** `eval/questions.yaml` has 30 public-safe questions; `eval/run_eval.py` measures recall@5 and MRR through the real Redis vector-search path. Two committed baselines: `fake-v1` (recall@5 0.4667, MRR 0.3078 — no semantic quality claim) and the real Titan baseline, **recall@5 0.8667, MRR 0.6917** (About Me 0.9333/0.7944, About System 0.8/0.5889) — the actual Phase 2 acceptance signal. ## Target architecture (full detail in docs/DESIGN.md)

Browser → Cloudflare (TLS/proxy) → Traefik on a single EC2 `t4g.small` (k3s) → FastAPI `api` (also serves the built frontend) + fixed-replica `retrieval-worker` ↔ in-cluster Redis (cache/queue/vector index) and MySQL (source of truth) → Amazon Bedrock (embeddings + LLM). KEDA scaling is planned for Phase 5.

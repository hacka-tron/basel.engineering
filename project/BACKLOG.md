## Multi-model pipeline notes (from the Phase 1b pilot, 2026-09-30)

- **Real integration tests that enqueue onto a shared, long-lived Redis Stream can pollute each other across test files if a test doesn't fully consume what it produced.** A test in `test_ask_endpoint.py` called the real `enqueue_retrieval_job` (correctly, to test real enqueue behavior) but simulated the worker's output directly instead of running a real worker to drain the job — leaving an orphaned, never-acked message sitting in `retrieval:jobs`. Redis Streams consumer groups deliver never-yet-delivered messages in stream order regardless of which consumer asks, so a *later* test file's brand-new consumer picked up that stale orphaned message instead of the one it had just added itself, and failed for a confusing reason (assertions about "the message I just enqueued" didn't match, because the code was actually processing someone else's leftover job). Symptom looked exactly like a real regression in freshly-changed code (a shared-helper refactor had just landed) and cost real time to root-cause via manual reproduction before the actual cause (test isolation, not implementation) became clear. **Lesson:** any integration test that enqueues real work onto a shared queue/stream must fully drain what it added (consume+ack, or delete the specific message) in a `finally` block — don't assume "my test passed" means "my test left no trace." Worth periodically checking `XLEN`/consumer-group lag on long-lived dev Redis instances if tests unexpectedly start failing for no code-visible reason.
- **The literal, manual "run the real thing end to end" step remains the actual bar, not passing tests.** All 72 automated tests passed before the real `curl -N` verification — but that verification is what actually proves DD1 Phase 1's done-when criterion (`docs/DESIGN.md` §17) is met: started the real worker and API processes, hit the real endpoint twice (once per corpus), and watched real `stage`/`retrieval`/`token`/`done` events stream correctly, `seq` staying strictly increasing across two separate OS processes sharing state only through Redis. No test suite, however thorough, is a substitute for this specific check when the deliverable's actual acceptance criterion is "watch it work."

## Data pipeline (M4 + deferred ingestion items)

- **M4 (DD3):** Google Drive + Git connectors, S3 raw zone, SQS + DLQ, KEDA ScaledJob ingestion, nightly reconciliation, blue-green re-embedding.
- **Ability to clear chunks** — an admin/ops path to wipe ingested chunks (Redis `idx:chunks` + the MySQL `chunks` table) for a clean re-ingest, rather than only ever accumulating/overwriting. Needs scoping when picked up: is this a CLI command (`python -m services.glassbox.ingest.run --clear` or similar), a debug-only API endpoint, or something else — and whether "clear" means one corpus, one embedding model's chunks, or everything.

Deferred from Phase 1a's ingestion script review (`services/glassbox/ingest/run.py`) — acceptable at current scale (174 chunks, local dev, single-worker batch script), worth revisiting if this ever runs under real concurrent load or against a much larger corpus:

- An `await` on the Redis write happens inside an open synchronous SQLAlchemy transaction — holds DB locks across network I/O, and if Redis writes succeed but the MySQL commit then fails, the two stores diverge for that document.
- N+1 query pattern: one `SELECT Document` per scanned file for the incremental hash check, plus a `session.flush()` per chunk insert instead of batching.
- The run-failure status update (marking `ingestion_runs.status='failed'`) isn't itself wrapped in error handling — if the failure was a MySQL disconnect, the status-update write will also fail and obscure the original error (though Python's exception chaining keeps the root cause in `__context__`, and the process still exits non-zero either way).

Documented as known limitations directly in code (docstrings) — not yet fixed, not urgent:

- `services/glassbox/ingest/chunkers/terraform.py`: brace-depth counting doesn't strip string literals/comments first, so an unbalanced `{`/`}` inside a Terraform string or comment would throw off block boundaries. No real `.tf` files exist yet (Milestone 2).
- `services/glassbox/ingest/chunkers/code.py`: decorator grouping only handles single-line decorators (a multi-line `@app.get(\n  "/x",\n)` would get orphaned); TypeScript matching doesn't cover typed arrow functions (`const f: Handler = (...) =>`) or generic type parameters. No real `.ts` files exist yet (frontend is a later phase).
- `services/glassbox/ingest/scanner.py`'s secret heuristic doesn't recognize GitHub/Slack/other provider-specific token formats, only AWS keys, private-key headers, and generic high-entropy assignments.

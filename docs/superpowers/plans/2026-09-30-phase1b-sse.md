# Phase 1b: API + Worker with the Full SSE Contract — Implementation Plan

> **For agentic workers:** Executed via the multi-model pipeline in `project/orchestration/` (Codex implements, Gemini reviews, orchestrator verifies end-to-end), same as Phase 1a.

**Goal:** Complete DD1 Phase 1 (`docs/DESIGN.md` §17): `curl -N` against `POST /api/ask` streams `stage`, `retrieval`, `token`, and `done` SSE events, backed by the real MySQL/Redis data from Phase 1a and the fake providers.

**Architecture:** Redis Streams as the job queue (`retrieval:jobs`), a retrieval worker consuming it via `XREADGROUP`, publishing progress over Redis pub/sub (`trace:{request_id}`). The API assigns a `request_id`, enqueues a job, subscribes to the trace channel, forwards events as SSE, builds a prompt from retrieved chunks, and streams the fake LLM's response.

**Tech Stack:** Same as Phase 1a — Python 3.12, FastAPI, `redis.asyncio`, SQLAlchemy. No new dependencies expected.

## Global Constraints

- **No caching layers, no rate limiting, no budget enforcement in this phase.** DD1 §17's own build plan puts the three cache layers and rate limiting in **Phase 2**, alongside real Bedrock providers — not Phase 1. Trace events for `answer_cache`/`embed_cache` nodes should exist (per the contract) but always report `cache: "miss"` in this phase; there's no cache to hit yet. Don't build caching logic now.
- **Trace event contract is exact — reproduce it verbatim** (from `docs/DESIGN.md` §8):

```ts
type NodeId =
  | "edge" | "api" | "answer_cache" | "queue" | "worker"
  | "embed_cache" | "embed" | "vector_search" | "mysql" | "llm";

type StageEvent = {
  request_id: string;
  seq: number;                 // strictly increasing per request
  node: NodeId;
  status: "start" | "end";
  t_ms: number;                // ms since request start
  duration_ms?: number;        // on "end"
  cache?: "hit" | "miss";      // for cache nodes
  meta?: Record<string, string | number>;
};

type RetrievalEvent = {
  chunks: { n: number; chunk_id: number; source_path: string; title: string;
            score: number; start_line?: number; end_line?: number; url?: string }[];
};

type TokenEvent = { text: string };

type DoneEvent = {
  total_ms: number;
  mode: "full" | "retrieval_only";
  answer_cache: "hit" | "miss";
  tokens_in?: number; tokens_out?: number;
};

type ErrorEvent = { code: "rate_limited" | "budget_exhausted" | "internal"; message: string; retry_after_s?: number };
```

  SSE format (also from §8):
  ```
  event: stage
  data: {"request_id":"01J...","seq":1,"node":"api","status":"start","t_ms":0}

  event: retrieval
  data: {"chunks":[{"n":1,"chunk_id":88,"source_path":"...","title":"...","score":0.87,...}]}

  event: token
  data: {"text":"The database runs on "}

  event: done
  data: {"total_ms":1840,"mode":"full","answer_cache":"miss","tokens_in":2900,"tokens_out":212}
  ```
  Only `rate_limited`/`budget_exhausted` error codes are unreachable in this phase (no rate limiting yet) — `internal` should still work for genuine failures.
- `request_id` format: ULID (26 chars) per DD1 §7.1's `queries.request_id CHAR(26)`. Use any correct ULID library, or a simple compliant generator if no new dependency is wanted — your call in the dispatch, note which you picked.
- Follow the repo layout: worker code under `services/glassbox/worker/`, API changes in `services/glassbox/api/`, shared trace/queue helpers under `services/glassbox/cache/` or `services/glassbox/retrieval/` per DD1 §16 (use judgment on exact placement, note it in the report).
- Use the dispatch templates in `project/orchestration/`. `gpt-6-sol` for implementation, `gemini-3.8-flash-medium` via `agy` (300-480s timeout) for review, orchestrator always verifies end-to-end against the real `docker-compose` stack before considering a task done.
- Commit after each task.

### Task 2: Redis Streams job queue + retrieval worker

**Files:**
- Create: `services/glassbox/worker/__init__.py`
- Create: `services/glassbox/worker/main.py` (entry point: `python -m services.glassbox.worker.main`)
- Create: `services/glassbox/retrieval/__init__.py`
- Create: `services/glassbox/retrieval/search.py` (vector search against `idx:chunks`)
- Test: `services/tests/test_worker.py`

**Spec (DD1 §6.3, §8):**

- Job queue: Redis Stream `retrieval:jobs`, consumer group `workers`. A job message contains at minimum: `request_id`, `question` (already embedded — see Task 3, the API embeds before enqueueing so the worker doesn't need the embedding provider), `embedding` (packed float32 bytes or similar), `corpus`.
- Worker loop: `XREADGROUP` on `retrieval:jobs`/`workers` (one message at a time is fine for this phase — no need for batching or KEDA-style concurrency yet, that's Phase 5), for each job:
  1. Publish a `stage` event (`node: "vector_search"`, `status: "start"`) to `trace:{request_id}` (Redis pub/sub channel).
  2. Run KNN vector search against Redis's `idx:chunks` index (already populated by Phase 1a's ingestion), filtered by `corpus` (tag filter), top 8 results (per DD1 §6.3).
  3. Fetch full chunk text + metadata (`source_path`, `title` — derive title same way the ingestion script does, or store it; your call, check what's available) from MySQL for the matched chunk IDs (no chunk cache yet — direct MySQL read each time, that's fine for this phase).
  4. Publish a `stage` event (`node: "vector_search"`, `status: "end"`, `duration_ms`).
  5. Publish a `retrieval` event with the matched chunks (per `RetrievalEvent` shape above — `n` is 1-indexed rank, `score` is the vector similarity score from the search).
  6. `XACK` the message.
- Emit `stage` events for the `mysql` node too (start/end around the chunk-text fetch step), separate from `vector_search`.
- If a job's referenced document/chunks are somehow missing (shouldn't happen given Phase 1a's data, but defend against it), publish an error rather than crashing the worker loop — the worker process should keep running and processing subsequent jobs even if one job fails.

**Testing:** integration-style against the real Redis/MySQL from `docker-compose` (same pattern as Phase 1a's `test_ingest_run.py` — don't over-mock). Cover: a job for a real `about_me` question gets a `retrieval` event with plausible results (real chunks from the real corpus, since Phase 1a's data already exists), the worker acks the message, a nonexistent-chunk edge case doesn't crash the worker loop.

### Task 3: API `/api/ask` SSE endpoint

**Files:**
- Modify: `services/glassbox/api/main.py` (add the route)
- Create: `services/glassbox/api/ask.py` (route logic, kept out of `main.py` to keep that file focused on wiring, per Phase 0's established pattern)
- Create: `services/glassbox/api/sse.py` (SSE formatting helper — `event: X\ndata: Y\n\n` framing)
- Test: `services/tests/test_ask_endpoint.py`

**Spec (DD1 §6.2, §8):**

- **Seq/t_ms convention (established by Task 2's fix round, read `services/glassbox/worker/main.py` for the exact mechanism before starting):** `seq` for every event on a request — whether emitted by the API or the worker — comes from `INCR seq:{request_id}` in Redis, so both processes draw from one shared, strictly-increasing counter. The API must use this same Redis key/pattern for its own emitted events, not a local counter. `t_ms` is `(current_time_ms - request_start_ts)`, where `request_start_ts` is set once, by the API, at the moment the request begins, and passed to the worker via the job payload (`enqueue_retrieval_job`'s `request_start_ts` parameter — already threaded through by Task 2). The API computes its own `t_ms` the same way, from the same `request_start_ts` value it generated.
- `POST /api/ask`, body `{"question": str, "corpus": "about_me" | "about_system"}`. Response: SSE stream, `Content-Type: text/event-stream`.
- Flow:
  1. Assign a `request_id` (ULID) and `request_start_ts` (epoch ms, generated once, now). Emit `stage` (`node: "api"`, `status: "start"`, `t_ms: 0`, `seq` from `INCR seq:{request_id}`).
  2. Emit `stage` (`node: "embed_cache"`, `status: "end"`, `cache: "miss"`) — no real cache in this phase, always miss (see Global Constraints).
  3. Emit `stage` (`node: "embed"`, `status: "start"`) → call `FakeEmbeddingProvider.embed([question])` → emit `stage` (`node: "embed"`, `status: "end"`, `duration_ms`).
  4. Emit `stage` (`node: "answer_cache"`, `status: "end"`, `cache: "miss"`) — always miss this phase.
  5. Emit `stage` (`node: "queue"`, `status: "start"`) → push the job onto `retrieval:jobs` (Task 2's queue) with the embedding, question, corpus, `request_id` → emit `stage` (`node: "queue"`, `status: "end"`).
  6. Subscribe to `trace:{request_id}` (Redis pub/sub) and forward every `stage`/`retrieval` event the worker publishes as SSE, as they arrive.
  7. Once the `retrieval` event arrives, build a prompt from the retrieved chunks (a simple, reasonable prompt template — cite chunk numbers, instruct the model to answer only from context — this doesn't need to be elaborate since it's going to a fake LLM anyway, but write it as if it mattered, since Phase 2 swaps in the real provider using the same prompt-building code).
  8. Emit `stage` (`node: "llm"`, `status: "start"`) → call `FakeLLMProvider.generate(prompt, max_tokens=400)`, emit a `token` event per chunk yielded by the generator, as it's yielded (real streaming, not buffered) → emit `stage` (`node: "llm"`, `status: "end"`, `duration_ms`).
  9. Emit `done` (`total_ms`, `mode: "full"`, `answer_cache: "miss"`, `tokens_in`/`tokens_out` — reasonable estimates, e.g. word counts of the prompt/response since there's no real tokenizer yet).
  10. Write a row to the `queries` table (Task 1): `request_id`, `corpus`, `question`, `cache_status='miss'`, `mode='full'`, `chunk_ids` (JSON array of matched chunk IDs), `stage_timings_ms` (JSON of node→duration_ms), `total_ms`, `tokens_in`, `tokens_out`.
- Use `seq` strictly increasing across the whole request (not per-stage) — a single counter incremented on every `stage` event emitted, per the contract.
- Use `fetch` with a streaming body reader parsing SSE on any client that consumes this (not relevant to this task's server-side implementation, just don't accidentally build something that requires `EventSource`, which can't POST — DD1 §6.1 flags this explicitly for future frontend work).
- **Timeout/failure handling:** if the worker doesn't publish a `retrieval` event within a reasonable timeout (e.g. 30s), emit an `error` event (`code: "internal"`) and close the stream cleanly rather than hanging forever.

**Testing:** integration-style — this needs the worker (Task 2) actually running to produce real results, OR the test can enqueue a job and directly publish to the trace channel to simulate the worker's output if running an actual worker process in tests is impractical (your call — note which approach you took and why). At minimum: a full `/api/ask` call against a real question from the real corpus produces a valid SSE stream with `stage`, `retrieval`, `token`, and `done` events in the right order, and a `queries` row gets written.
